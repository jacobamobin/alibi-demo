# Alibi native iOS design and phone proof plan

Date: November 1, 2026 (America/Toronto).

Status: reviewed design proposal; product implementation has not begun. An independent iOS builder review found no material unanswered planning questions. The user selected one live agent, native iOS, no application backend, synthetic test contacts/photos, and a maximum of 10 voices in a call. SwiftUI and the staged delivery below are implementation recommendations.

## 1. Product and success

Alibi is an improvised AI group-call experience with a FaceTime-style interface. A person starts a scenario, talks naturally, and brings characters into the call by name. Each character has a persistent identity, portrait, personality, voice, and access to the conversation's shared context.

The first demonstration runs as an installed application on the user's physical iPhone, reported to be running iOS 26.0. It uses live provider responses. A simulated UI or simulator recording alone does not establish that the phone proof works.

The test dataset is synthetic, as explicitly clarified by the user: both the contacts/photos already on the test phone and the characters generated by Alibi represent fictional people. Profile estimates are fictional character attributes, not verified biographical facts.

## 2. Approaches and chosen direction

| Approach | Outcome |
| --- | --- |
| Static React/Next.js application with an ElevenLabs agent | Original proposal; superseded by the user's request for a native iOS application. |
| Native application with a separate conversational agent for every person | Considered; user selected one live agent performing the cast instead. |
| Native SwiftUI application with one ElevenLabs multi-voice agent | Recommended implementation of the selected direction. Direct native integrations for audio, Contacts, Photos, Keychain, and a share extension. |
| React Native application with the same agent | Feasible, but adds native bridging without a current cross-platform delivery requirement. |

No custom server, serverless function, hosted database, account system, or application proxy is required for the personal test build. Provider services still run remotely, and live features require an internet connection. The phone communicates directly with ElevenLabs and, when enabled, OpenAI using the device owner's credentials.

## 3. Native application

Proposed first device target: iOS 26.0. The earlier question about an iOS 16 runtime was followed by confirmation that the test phone runs iOS 26.0; older-device compatibility is not a prerequisite for this proof.

Use SwiftUI, the ElevenLabs Swift SDK, URLSession for auxiliary REST requests, Keychain for credentials, and local storage for profiles/context/portraits. Resolve and pin a released SDK version during implementation; inspected upstream main is evidence of available interfaces, not a pinned dependency.

Primary screens:

- **Calls:** start/resume a scenario, recent local sessions, choose initial participants.
- **People:** imported and generated fictional characters, portrait, editable profile, relationship/context notes, voice preview and voice selection.
- **Context:** scenario brief, imported material, source references, generated profile details, and the current call's shared facts.
- **Settings:** ElevenLabs key, agent ID, optional OpenAI key, credential checks, model configuration, and local data controls.
- **Active call:** FaceTime-style dark participant tiles, circular profile photos, names, call timer, add-person control, mute, audio route, and end-call controls. Preserve the Alibi app identity and simulated-character context. The user's UI kit is still forthcoming.

Use the agent's built-in conversation handling for listening, turn-taking, interruptions, and speech. Validate behavior on speakerphone and headphones. Do not claim per-character speaking highlights are synchronized until voice labels and audio timing have been verified against the SDK's actual events.

## 4. Two character sources

### A. Synthetic contacts and photos already on the test iPhone

1. Import selected contacts through the native contact picker. Retain the source-local contact identifier and available name/photo fields.
2. Use the contact's photo when available, or let the user assign one or more synthetic photos through PhotosPicker. An image without a contact is also a valid starting point.
3. Do not assume iOS automatically exposes the identity of everyone pictured in the photo library. Contact-to-photo association is explicit in the first version.
4. Submit the selected synthetic portrait to OpenAI when the user requests profile generation. Produce an apparent adult age range, fictional race/ethnicity description, fictional nationality, gender/pronouns, personality, relationship notes, and a desired voice description.
5. Keep the original contact fields and image separately from generated attributes. Display these outputs as editable fictional estimates with their source portrait and generation provenance.
6. Create a voice brief with vocal age, masculine/feminine/androgynous presentation as appropriate to the fictional profile, accent, pitch, texture, pace, and emotional style. Audition suitable ElevenLabs voices and save the chosen voice ID. Avoid hardcoded race-to-accent rules; nationality and voice accent are distinct character attributes.

The result is a plausible voice for the fictional profile. Reproducing a particular sound requires reference audio and a separate permitted cloning flow; a photo does not contain a recording of someone's voice.

Selected-contact and selected-photo import are part of the initial integration. Bulk Contacts access or limited/full PhotoKit library access may be added later with the corresponding native authorization. These broader permissions are not required to prove the two-source character flow.

### B. Characters Alibi generates on demand

1. The user says, for example, "I was with John."
2. The live agent asks the native app to resolve John against saved names and aliases.
3. A unique match reuses the saved character. Ambiguous matches return choices; do not silently bind to the wrong person.
4. No match creates a new fictional character with a first name, invented surname, personality, relationship to the scenario, and voice brief. Explicit pronouns supplied by the user guide the fictional profile; unspecified details can be authored by the model.
5. Assign an available prepared voice slot and add the participant to the call. Generate a new synthetic portrait through OpenAI asynchronously; show initials/a placeholder while it loads.
6. Save the character so later references reuse the same identity, voice, portrait, and remembered fictional details.

Names alone do not trigger creation when merely mentioned in passing. A join request, an explicit add-person action, or agent reasoning that another participant should join invokes the join tool.

## 5. One agent, ten voices, dynamic joining

The user accepts a maximum of 10 people/voices per call. ElevenLabs documents a maximum of 10 configured voices per multi-voice agent, including its default voice. Reserve one distinct voice ID per active character in the proof.

Prepare the call's supported voice roster before establishing the live connection. It includes selected saved characters' exact voice IDs and spare stock/generated-voice presets for people invented during the call. Participants can remain off-call until they join; configuring a voice is separate from making that character a participant.

Adding a character dynamically updates native call state and agent context within the same session. The model uses the corresponding configured voice label when that person speaks. Everyone shares one conversation history, with distinct personality instructions attached to each character.

Do not assume a previously unconfigured voice can be inserted into an already active audio session. The inspected Swift TTS override exposes a primary voice ID and voice settings, not a live supported-voices replacement API. Prove this boundary before promising arbitrary new custom voices mid-call.

If a saved character's exact voice was not prepared, show that it needs preparation before a new session; do not silently substitute a different saved voice. Newly invented people can use remaining prepared slots. When all 10 slots have identities, reject an additional distinct voice for that session. The first proof does not recycle slots after someone leaves.

Start the voice spike with one dedicated agent configured with three voices in the ElevenLabs dashboard. This avoids making automated agent administration a dependency of the first microphone test. Add native pre-call roster preparation through the owner's ElevenLabs API key only after that spike works. Do not mutate an agent used concurrently by unrelated test sessions.

Proposed client tools:

| Tool | Native behavior |
| --- | --- |
| `lookup_character` | Resolve a name/alias in the local library; return a match, ambiguity, or no match. |
| `join_character` | Validate the profile and available voice slot, add one participant, return its ID and exact voice label. |
| `leave_character` | Remove a participant from the active cast while retaining the saved profile. |
| `update_shared_context` | Add or revise explicit fictional scene facts in the current session. |

Deduplicate retries by tool-call ID and character ID. An asynchronous portrait completion must not recreate a removed participant or update a later call. Send native context changes using the SDK's contextual-update interface; inspect the selected release rather than copying a React method name into Swift.

## 6. Context and sharing on iOS

Yes: an iOS share extension can receive supported content that the user explicitly shares from another application. The full target supports text, links, images, and exported contact files where the source app provides them. A shared item appears in a local inbox, where the user assigns it to a character or scenario and reviews the extracted context.

An App Group shared container connects the extension and Alibi. The extension stages imports; the containing app owns profile generation and provider calls. Validate signing entitlements before adding the extension to the phone build. If the selected signing team cannot provision the capability, retain in-app pickers/manual paste for the first proof and report share-extension testing as pending.

This does not provide automatic access to private iMessage threads, FaceTime history, other apps' databases, or all phone content. Source applications decide what they expose through sharing. A Messages-like screen, if later added, is an Alibi simulation rather than access to Apple's message store.

Shared context is scoped per call and character. The agent gets the relevant approved text and character descriptions, not the whole contact or photo library. Synthetic photo analysis uses only images selected for that request. Treat imported text as data, not authority to execute arbitrary tools.

## 7. Credentials, storage, and service boundaries

The personal test build is bring-your-own-key. Enter provider keys in Settings and store them in Keychain, with device-only accessibility suitable for foreground calls. Do not place keys in source files, build settings, preferences, shared app-group files, logs, transcripts, or screenshots. Each additional tester supplies their own credentials.

The native client can request a conversation credential directly from ElevenLabs using its owner's key, then pass that temporary credential to the Swift SDK. This owner-operated flow needs a live integration check; provider examples generally assume a backend holds a developer-owned shared secret. A public demo agent ID is a separate fallback for the fixed-roster voice spike, not proof that private authentication works.

OpenAI is an auxiliary profile/image service, not a second live call participant. Use explicit model configuration and structured profile outputs. Cache profiles and portraits locally. A missing OpenAI key still permits calls with already prepared characters; imported-portrait analysis and fresh portrait generation stay unavailable until configured.

One new-character portrait request per join by default. Deduplicate automatic retries and offer explicit retry after a failure. No paid requests, photo uploads, provider-agent creation, or voice cloning have been executed during planning.

Retain source imports, generated attributes, selected voice IDs, and context separately. Sessions and transcripts are local by default. Provider-side conversation/audio retention follows the provider account configuration and must be inspected during setup; local storage does not imply provider-side non-retention. iCloud sync and a Mac companion are later work.

## 8. Build and physical-device prerequisites

Observed on this Mac: macOS 26.7.1; the active developer directory is `/Library/Developer/CommandLineTools`; no Xcode app was found in `/Applications` or `~/Applications`; `xcodebuild` and `devicectl` are unavailable; no iPhone was detected in the USB inventory. These observations do not establish wireless pairing status.

The user reports iPhone iOS 26.0. Confirm the model and exact version when pairing. Apple's current compatibility table lists Xcode 27.2 as compatible with macOS 26.6 or later and physical iOS 17-or-later devices, which includes this reported phone. Xcode 26.6 is another listed compatible option for this Mac and iOS 26 devices. Prefer an available stable compatible release from Apple; do not install an obsolete iOS 16 simulator for a physical iOS 26 test.

Use [Apple's Xcode download entry point](https://developer.apple.com/xcode/) and, for a specific version, [More Downloads](https://developer.apple.com/download/all/?q=Xcode). The latter requires Apple sign-in. No Xcode installer or runtime has been downloaded during this planning pass.

For physical testing: install full Xcode and its required iOS platform components; complete Apple-controlled sign-in/license steps; select the full Xcode developer directory; pair the phone, enable Developer Mode if requested, select the signing team, and install the app. A separate simulator OS runtime is optional for simulator tests. A free Personal Team can support basic device testing with Apple's provisioning limits; advanced entitlements require checking the selected team's capabilities.

## 9. Ordered delivery and acceptance evidence

### Stage 0: unblock the device toolchain

Install/select Xcode, resolve the SDK against the deployment target, pair the iPhone, and run a minimal signed native application. Record the Xcode version, iPhone model/iOS, signing mode, build result, and physical launch. App compilation alone is not device installation.

### Stage 1: prove one live agent with three voices on the phone

Use three synthetic fixture profiles and one dedicated, fixed-roster ElevenLabs agent. Start with one participant. Demonstrate live microphone input and responses, then add two prepared characters during the same conversation. All three must speak in their assigned voices, preserve distinct personalities, and recall an earlier shared scene fact. Verify mute, interruption, end-call cleanup, and a clear network-error state. Save a short device demonstration and sanitized session evidence.

This stage proves the central product behavior before contact import, portrait inference, or a polished call screen can obscure an audio integration failure.

### Stage 2: prove the two character sources

Import one synthetic contact and its selected synthetic portrait on the phone. Generate and inspect its fictional profile, audition a suitable voice, prepare that voice for the next session, and reuse the saved identity. In the same session, request an unknown name; generate its identity, assign a remaining prepared voice, add the tile immediately, and replace the placeholder when a newly generated portrait arrives. Retrying the tool must not create duplicates or duplicate portrait charges.

### Stage 3: finish the native experience and sharing

Apply the supplied UI kit to the agreed FaceTime-style layout, add character/context editors, and test Contacts/Photos cancellation and missing-image cases. Add the share extension if signing supports it. Prove one shared photo and one shared text item enter Alibi and influence the selected fictional scene only after review.

### Completion criteria

- An actual signed Alibi application runs on the user's iPhone with no custom application backend.
- One live agent maintains a coherent scene and distinct personalities/voices as three people join dynamically.
- Both synthetic-source import and unknown-name generation work end to end.
- The app enforces the 10-voice/session limit and preserves exact prepared voice bindings.
- Credentials survive an app restart through Keychain and remain absent from repository files and diagnostic output.
- Device evidence distinguishes tested behavior from remaining SDK, signing, sharing, and timing limitations.

## 10. Remaining choices and implementation latitude

The builder may choose internal file organization, local persistence details, request cancellation mechanics, portrait cropping, JSON validation library choices, and a compatible released SDK after inspecting the toolchain. No additional product decision is needed for those choices.

At implementation setup, inspect the phone, signing account, provider plans/model access, voice inventory, agent configuration, and the promised UI kit. These are operational inputs; lack of them must not be represented as a successful device proof. Test private conversation authentication, prepared-roster joins, and speaker attribution before promising those integrations.

The design is ready for user review. The next implementation plan should cover the Stage 0/1 phone proof first, followed by the two-source profile integration and share extension as separate reviewable milestones.
